# Учёт деталей — производственное приложение

Мобильное веб-приложение для мастеров участка: учёт изготовленных деталей по станкам,
автоматический расчёт выработки за час/смену, формирование текстовых отчётов и их
ежечасная автоматическая доставка в мессенджер.

## Технологии

| Слой | Технология | Почему |
|---|---|---|
| Клиент (телефон) | React + Vite (PWA) | Ставится на телефон как приложение, работает офлайн, один код под Android/iOS |
| Сервер / БД | Supabase: PostgreSQL + Auth + Realtime + Edge Functions | Многопользовательский доступ из коробки, готовая авторизация, мгновенное обновление данных у всех пользователей |
| Отчёты в мессенджер | Android Share Sheet (`navigator.share`) → мессенджер MAX | Отправка стандартными средствами телефона: приложение формирует текст, Android открывает выбор приложений, мастер выбирает MAX и общую группу. Серверных ботов и API мессенджера не требуется |

## Структура данных (схемы)

### Справочники
- **shifts** — бригады: `А`, `Б`, `В`, `Г` (+ тип: день/ночь)
- **machines** — станки (сейчас 12, количество не ограничено). Поля: порядковый номер, модель (`СК 61125`, `Neway VNL80HA`, `Lunan CK611`…), участок/ВАИС (`003`, `304`, `305`), группа (`Линия`, `РМУ`, `Карусельный`), признак активности
- **people** — люди: ФИО, роль (`мастер`, `оператор`), статус (`ученик` и т.п.)
- **parts** — номенклатура деталей: артикул/чертёж, название, участок/ВАИС, примечание («Лыска»).
  Детали постоянные, но появляются новые — реализовано добавление и редактирование из приложения
  (доступно админу и мастерам). Здесь же фиксируется **норма выработки** (`norm_hours`) —
  используется для % выполнения и будущих табелей. Снятие с производства = флаг «не активна»,
  история не удаляется.
- **part_operation_plans** — таблица планов (редактируется отдельно): деталь + станок +
  операция (ток) → план на смену в штуках. Задаётся один раз для типа детали и подхватывается
  автоматически при открытии смены; изменение плана не переписывает прошлые отчёты
  (история правок планов сохраняется)

### Офлайн-режим и синхронизация (интернет нестабильный, мобильный)
Приложение работает как PWA с локальной базой на телефоне (**SQLite через Capacitor**, Android-обёртка
над тем же кодом React):

1. Мастер вводит данные со счётчиков **без интернета** — всё сразу пишется в локальную базу телефона,
   ничего не теряется даже при закрытии приложения или разряде телефона.
2. Каждая запись имеет `uuid` (генерируется на телефоне), `client_seq` (порядок внутри телефона)
   и `author_id` (кто внес). Это позволяет корректно слить данные от нескольких мастеров.
3. Как только появляется сеть, фоновый модуль синхронизации выгружает очередь «outbox» в Supabase
   (повторяющиеся попытки, идемпотентность по uuid — дублей не будет).
4. Разрешение конфликтов: почасовая выработка считается по временным меткам замеров, а не по порядку
   прихода записей, поэтому два мастера могут вносить данные независимо — итоги всё равно корректны.
   Одинаковый станок+ток+время от двух мастеров = одна запись (дубликат отбрасывается на сервере).
5. Отчёт формируется из локальных данных мгновенно, без ожидания сети.

### Оперативные данные
- **shift_sessions** — смена привязана к дате и бригаде; **несколько мастеров в одной смене**
  (`session_masters`: мастер + время начала/конца дежурства). Бывают смены, где 2 мастера сменяются
  посменно — каждый собирает данные в своё время, оба имеют право править эту смену.
  Каждый замер хранит `recorded_by` — кто именно его внёс (видно в детализации и табелях v2).
- **assignments** — расстановка: оператор ↔ станок(и) в течение смены.
  Один оператор может вести несколько станков; выход на РВД в другую смену помечается флагом `is_rvd`
- **operations** — токи/переходы по детали на станке: `Ток 1`, `Ток 2`, `Ток 3`, `доработка`…
  план подтягивается из `part_operation_plans` (например: Ток 1 — план 24, Ток 2 — план 35)
- **production_entries** — записи мастера при обходе: станок, операция, деталь, время,
  **значение счётчика станка на текущий момент** (`counter_value`). Мастер ничего не считает —
  только переносит цифры со счётчика. Программа сама высчитывает:
  - выработку за час = разность последних замеров часа (пример: 9:00→10:00 Ток 1 = 2 шт.,
    10:00→11:00 Ток 1 = 3 шт., накоплено 5),
  - выработку за смену = последний замер − начало смены,
  - «за час / накоплено» и «сделано/план» по каждому току, как в отчёте (`Ток 3 — 4/7шт.`)
  - падение значения счётчика = сброс после переналадки (отмечается отдельно), расчёт продолжается
    корректно
- **downtimes / статусы станка** — причины простоя: `нет задела`, `нет заготовки`,
  `ожидание ремонта ШВП`, `не в работе` — выводятся в отчёт отдельной строкой
- **changeovers** — переналадки: время, станок, с какой детали на какую (влияет на почасовой расчёт)

## Роли и права доступа

Реализуются через Row Level Security (RLS) в Supabase — правила применяются на уровне базы,
обойти их из приложения невозможно.

| Роль | Справочники (станки, люди, детали+нормы, планы) | Данные смены | Прочее |
|---|---|---|---|
| **Админ** | чтение + редактирование | полный доступ ко всем сменам (создание/правка/удаление) | шаблоны отчётов, пользователи, настройки |
| **Мастер** | чтение + редактирование | только смены, к которым он **привязан как мастер дежурства** (`session_masters`): если в смене два мастера — оба могут править эту смену; данные чужих смен изменить не может | формирование и отправка отчётов своей смены |
| **Оператор** (опционально) | только чтение | просмотр своих станков | — |

Правило для мастера: запись `production_entries` доступна на изменение мастерам, входящим в
`session_masters` этой смены. Мастер смены А физически не сможет изменить данные смен Б, В, Г —
база отклонит такую операцию. При смене мастера посреди смены достаточно добавить второго мастера
в `session_masters` с временем начала дежурства — права появятся автоматически.

## Долгосрочная статистика (этап v2 — «закрытие табелей»)

Цель — статистика по операторам для закрытия табелей. Реализуется позже, но все данные
накапливаются с первого дня (каждая запись обхода привязана к оператору, смене, детали):
- агрегаты по оператору за месяц: штуки по деталям, смены, % выполнения нормы (`norm_hours`);
- выгрузка в файл (CSV/XLSX) и отправка через тот же Share Sheet → MAX.

## Настройки
- `report_lead_minutes` — за сколько минут до конца часа формируется отчёт (по умолчанию 15,
  значение настраивается админом).

### Отчёты и рассылка
- **report_templates** — шаблон текста отчёта (по умолчанию воспроизводит ваш формат):
  ```
  СК Линия: 03.10.26 — «день»
  Бригада «В»
  Отчёт на 11:00

  0. СК 1680 (ВАИС 003) - Александров А.А. (ученик)
   Ток 1 — 0/0 шт.
   План: 24 шт (нет задела на ток1)
  ...
  ```
- **report_logs** — история сформированных и отправленных отчётов (что, когда, кому доставлено)
- **channels** — куда слать: общая группа в мессенджере MAX. Так как отправка идёт через
  Android Share Sheet, chat_id не нужен — мастер выбирает группу при отправке; приложение
  запоминает последний выбор и подсказывает его

## Как это работает (поток)

1. Мастер открывает приложение на телефоне, выбирает (или подтверждает) свою смену;
   если в смене два мастера — каждый работает под своим аккаунтом, данные не конфликтуют.
2. Видит список станков своей смены с текущими показателями. Подходит к станку,
   в пару касаний вводит: станок → операция → **значение счётчика на текущий момент** (+ примечание/простой).
   Работает без интернета: записи копятся локально и уходят на сервер при появлении сети.
3. Почасовые и сменные итоги считаются автоматически по времени замера
   («за час / накоплено», как `Ток 3 — 4/7шт.`).
4. За `report_lead_minutes` минут до конца часа приложение показывает напоминание «Отчёт на HH:00 готов»
   (звук + уведомление). Мастер нажимает «Отправить» → стандартный Android-механизм обмена → MAX → общая группа.
   Отчёт можно сформировать и отправить вручную в любой момент; факт отправки фиксируется в истории.
5. После синхронизации все изменения видны всем пользователям (Realtime для админа и других мастеров).
6. Права проверяются на уровне базы (RLS): мастер видит и правит только свои дежурные смены,
   админ — всё; справочники доступны мастерам для редактирования.

## Этапы разработки

1. **MVP (1–2 недели):** схема БД + RLS-роли, авторизация, офлайн-хранилище на телефоне (SQLite/Capacitor),
   экран обхода станков с быстрым вводом значения счётчика, таблицы деталей и планов, формирование текста отчёта.
2. **Синхронизация и отправка:** фоновая выгрузка outbox в Supabase при появлении сети, разрешение дублей,
   кнопка «Поделиться» (Android Share Sheet → MAX), история отчётов, почасовое напоминание со звуком.
3. **Доработка:** переналадки, РВД, графики выработки, экраны администрирования справочников.
4. **v2 — табеля:** долгосрочная статистика по операторам, % выполнения норм, экспорт CSV/XLSX.

## Вопрос для продолжения

Как мастера будут получать доступ в приложение — админ заранее создаёт каждому логин и временный пароль
(мастер меняет при первом входе), или нужна регистрация по номеру телефона с SMS-кодом?
И второй подсказывающий вопрос: телефон у мастера один на участок или у каждого мастера свой?
